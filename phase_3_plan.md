## Зачем Redis здесь (рамка, чтобы не cargo-cult'ить)

Дашборд агрегирует: **месячный ФОТ** (total monthly payroll cost), **headcount по департаментам**,
**среднюю зарплату по грейдам**, **суммарную налоговую нагрузку**. Эти цифры дороги в пересчёте
(проход по зарплатам всей компании) и меняются редко (найм/увольнение/смена зарплаты — события
не ежесекундные) → классический профиль **cache-aside**. Плюс **справочники** (departments,
positions для дропдаунов будущего фронта) — почти статичные данные, второй классический кэш-профиль.

**Ключевой сдвиг относительно Фазы 2.** MediatR дал шов диспетчеризации; кэш — первая
**инфраструктурная зависимость на query-стороне**. Урок фазы: кэш — это не «ускорить», это
**осознанная сделка со свежестью данных**. Поэтому staleness тут не баг, а задокументированное
решение с известным сроком жизни (TTL) и запланированной заменой на событийную инвалидацию в Фазе 4.

## Locked-in решения (не пересматривать на пустом месте)

- **Инвалидация в этой фазе — только TTL.** Краткая staleness принимается и документируется.
  Phase 4 (domain events: `EmployeeFired`, `SalaryChanged`, …) заменит TTL на event-driven eviction —
  это **запланированный рефакторинг, не оверсайт**. Следствие уже сейчас: все ключи кэша живут
  в **одном каталоге** (статический класс), чтобы Фазе 4 было что эвиктить по имени.
- **Кэшируем на уровне query-хендлеров (Application).** Не в репозиториях (они про персистентность,
  а не про свежесть) и не HTTP output caching (он про ответы целиком, без контроля ключей и без
  шва для будущей событийной инвалидации). Output caching — прочитать и **осознанно отвергнуть**.
- **API кэша — `HybridCache`** (`Microsoft.Extensions.Caching.Hybrid`, работает на net8) поверх
  Redis как L2 (`AddStackExchangeRedisCache`). Причина: `GetOrCreateAsync` — готовый cache-aside +
  **защита от stampede из коробки** (single-flight). `IDistributedCache` остаётся обязательным
  prerequisite reading — это фундамент, поверх которого HybridCache построен.
- **Feature first, cache second.** Блок 2 строит эндпоинты БЕЗ кэша с полным покрытием;
  блок 3 добавляет кэш как behavior-preserving слой. Иначе не отличить «кэш сломал логику»
  от «логика была кривой».
- **Git workflow прежний:** ветка = логический блок, master релизопригоден, мержим только зелёное.

## Prerequisite reading (уложить в голову ДО кода)

1. **Cache-aside vs read-through vs write-through** — `cache-aside pattern`. Понять, почему aside.
2. **Cache stampede** — `cache stampede thundering herd`. Что происходит в момент истечения TTL
   под нагрузкой и что такое single-flight.
3. **Три уровня кэш-API в .NET** — `IMemoryCache vs IDistributedCache vs HybridCache`.
   Кто где живёт (процесс vs Redis), кто что гарантирует.
4. **Output caching .NET 8** — `output caching middleware .NET 8`. Прочитать, чтобы отвергнуть
   аргументированно (см. locked-in).
5. **`ConnectionMultiplexer` — singleton** — `StackExchange.Redis ConnectionMultiplexer singleton`.
   Почему соединение одно на процесс, а не на запрос.

## Блок 1 — Redis-инфраструктура

### Цель
Redis поднимается вместе с постгресом, приложение к нему подключается, health check отражает
состояние. Никакой бизнес-логики — только провода.

### Направление
- `redis:7-alpine` в docker-compose по образцу postgres: порт из `.env` (`REDIS_PORT`),
  healthcheck `redis-cli ping`, named volume не нужен (кэш эфемерен по определению — потеря
  содержимого легальна).
- Строка подключения — в `appsettings.local.json`, как у БД.
- Регистрация: `AddStackExchangeRedisCache` (L2) + `AddHybridCache` — в
  `ServiceCollectionExtensions` по образцу существующей инфраструктуры.
- Health check: `AddRedis(...)` рядом с существующими `AddNpgSql`/`AddDbContextCheck`,
  со своими тегами (`cache/redis/live`).

### Ловушки
- **Не создавать `ConnectionMultiplexer` руками на запрос** — `AddStackExchangeRedisCache`
  управляет соединением сам. Ручной мультиплексор понадобится только Фазе 4 (pub/sub-инвалидация) —
  не тащить сейчас.
- **Падение Redis ≠ падение дашборда.** Реши политику заранее: fail-open (кэш недоступен →
  считаем из БД, пишем warning) или fail-fast (500). Рекомендация — fail-open: кэш — оптимизация,
  а не источник истины. Проверь, как ведёт себя HybridCache при недоступном L2 (L1 остаётся жив),
  и зафиксируй поведение интеграционно или хотя бы в README фазы.
- `InstanceName`/префикс ключей задать сразу — чтобы в одном Redis могли жить несколько
  окружений/тест-ранов, не путаясь в ключах.

### Что гуглить
`AddStackExchangeRedisCache configuration`, `HybridCache .NET 8 AddHybridCache`,
`AspNetCore.HealthChecks.Redis`, `docker compose redis healthcheck`.

## Блок 2 — Дашборд и справочники (БЕЗ кэша)

### Суть фичи
- `GET /v1/reporting/dashboard` — один эндпоинт, один DTO с четырьмя агрегатами:
  месячный ФОТ, headcount по департаментам, средняя зарплата по грейдам, суммарный месячный налог.
  Один эндпоинт (а не четыре) — сознательно: один ключ кэша в блоке 3, один эвикт в Фазе 4.
  Пер-агрегатные ключи — усложнение, которое никто не запросил.
- `GET /v1/departments`, `GET /v1/positions` — справочники для дропдаунов. Плоские списки, без пагинации
  (объём справочников её не оправдывает).

### Направление
- Обычные MediatR queries + хендлеры, как в блоке 3 Фазы 2. Контроллер тонкий.
- **Где считать:** headcount и среднюю по грейдам — агрегацией в БД (`GroupBy` → `Select`,
  проекция, без загрузки сущностей). ФОТ и налоги — тоньше: конверсия зарплаты к месяцу и
  `CalculateTaxes()` — **доменная логика**, в SQL её не переведёшь без дублирования формулы
  (а дубль начнёт врать при первом изменении). Активная зарплата — одна на сотрудника, объём мал →
  грузить проекцией только нужные скаляры (`Amount`, `Type`) и считать доменом в памяти.
  Это осознанный компромисс — задокументируй его в хендлере одной строкой.
- Новые read-методы — в существующие узкие интерфейсы по их принадлежности (агрегаты по зарплатам →
  `ISalaryRepository`, headcount → `IEmployeeRepository`, справочники → `IDepartmentRepository`/
  `IPositionRepository`). Отдельный `IReportingRepository`-бог не заводить.

### Правила данных (зафиксировать до кода, проверить тестами)
- **Fired исключаются** из ФОТ, headcount и налогов. Уволенный с незакрытой зарплатой — баг данных,
  а не участник ФОТ (закрытие зарплаты при fire уже есть).
- Активная зарплата = `EndDate == null` — существующий инвариант, на него и опираться.
- Средняя по грейдам: `decimal`, округление зафиксировать (`Math.Round` до 2, полугодовое правило
  по умолчанию — banker's; осознать и записать).
- Пустая БД → нули и пустые коллекции, не 404 и не исключение.

### Тесты (value-first)
- Сиженные данные → руками посчитанные суммы (как в существующих ReportingTests).
- «Уволенный не считается»: fire → агрегаты уменьшились.
- «Смена зарплаты видна»: change salary → ФОТ отражает новую (это же станет базой для
  staleness-теста блока 3).
- Справочники: содержимое и порядок (детерминированный `OrderBy`).

### Что гуглить
`EF Core GroupBy projection`, `EF Core aggregate query performance`, `decimal rounding banker's`,
`REST reference data endpoint`.

## Блок 3 — Cache-aside поверх дашборда

### Цель
Обернуть query-хендлеры блока 2 в кэш с TTL так, чтобы регрессионная сеть осталась зелёной,
а повторный запрос не ходил в БД.

### Направление
- **Каталог ключей** — статический класс в Application (например, `CacheKeys`):
  `reporting:dashboard`, `lookups:departments`, `lookups:positions`. Версию формата ответа —
  в ключ (`:v1`): смена схемы DTO не должна читать старые байты.
- В хендлере: `HybridCache.GetOrCreateAsync(key, factory, options, ct)` — фабрика и есть
  прежнее тело хендлера. Больше ничего не меняется.
- **TTL из конфигурации**, не хардкод: агрегаты — короткий (1–5 мин), справочники — длинный (~1 час).
  Числа — в `appsettings` с осмысленными дефолтами.
- DTO кэшируемых ответов — неизменяемые (records), сериализация — System.Text.Json
  (та же политика, что у API: enum'ы строками уже настроены глобально — проверь, что кэш-сериализация
  им не противоречит).

### Тестирование кэша (главная методическая точка блока)
- **Интеграционно:** `Testcontainers.Redis` в `IntegrationFixture` по образцу `PostgreSqlContainer`.
- **Не тестируй тайминги TTL** («подождать 5 минут») — хрупко. Тестируй инварианты:
  1) два подряд запроса дают одинаковый ответ; 2) после мутации данных ответ дашборда **в пределах
  TTL легально stale** — это документирует поведение: мутация → запрос → старое значение →
  очистка ключа (или отдельный короткий TTL для теста) → новое значение.
- **Изоляция между тестами:** кэш — общее состояние, как БД. В `ResetAsync` фикстуры чистить Redis
  (`FlushDatabase`) рядом с Respawn'ом — иначе тесты начнут видеть чужие ключи и мигать.
- Юнит-тесты хендлеров: HybridCache абстрактен — либо фейк, либо считать кэш интеграционной заботой
  и юнитами покрывать только фабрику (рекомендация: второе, юнит на «математику», интеграция на кэш).

### Ловушки
- **Stampede** решён выбором HybridCache — но проговори себе, что именно он решает
  (одновременное истечение → один пересчёт, остальные ждут), чтобы на интервью не сказать «магия».
- **Не кэшировать ошибки:** фабрика бросила → в кэше ничего не должно осесть (HybridCache так и
  делает — но проверь, а не поверь).
- **Ключи только из каталога.** Строковый литерал ключа в хендлере — код-смелл: Фаза 4 будет
  эвиктить по этим же константам.
- Существующие reporting-эндпоинты (`/count`, `/salaries`, `/taxes`) **не трогаем** — кэш только
  на новом дашборде и справочниках. Расширить кэш на старые — отдельная гранула после, если захочется.
- Staleness задокументировать явно (README фазы или комментарий у TTL-конфига): «дашборд может
  отставать до N минут; снимается в Фазе 4 событийной инвалидацией».

### Что гуглить
`HybridCache GetOrCreateAsync tags`, `cache key versioning`, `Testcontainers.Redis dotnet`,
`integration testing distributed cache`, `cache stale read documentation`.

## Порядок действий
```
1. Блок 1: Redis в compose + подключение + health check → сеть зелёная (кэш ещё ничего не делает)
2. Блок 2: дашборд + справочники без кэша → новые тесты + сеть
3. Блок 3: каталог ключей + HybridCache в хендлерах + Redis в фикстуре → сеть зелёная + тесты кэша
```

## Задел на Phase 4 (RabbitMQ + domain events)
Каталог `CacheKeys` — это интерфейс между фазами: события `EmployeeFired`/`SalaryChanged`/
`LeaveApproved` будут эвиктить ключи по этим константам, заменяя TTL-компромисс на событийную
инвалидацию. Пока пишешь блок 3 — держи в голове: каждая мутация, влияющая на дашборд, это будущий
подписчик-эвиктор. Если поймаешь себя на желании «просто уменьшить TTL до секунд» — это сигнал,
что фича хочет Фазу 4, а не тюнинг компромисса.
